TASK 3: VALIDATION RULE — COMMAND MUST NOT BE EMPTY
---------------------------------------------------------------
WHAT:
  - Whenever a pod/deployment is annotated with the secret-inject annotation,
    there MUST be a validation rule that rejects the resource if
    spec.containers[*].command is empty or missing.

WHY:
  - Kubernetes `command` in pod spec REPLACES the Docker ENTRYPOINT -- it does
    NOT append to it.
  - A developer may think their Dockerfile ENTRYPOINT is enough and omit `command`
    from the manifest. This will break the secret injection wrapper.

WHERE TO ADD:
  - Add the validate rule INSIDE the same secret-injection ClusterPolicy file
    (Task 1), NOT as a separate file.
  - Do NOT keep a standalone "require-command-on-annotated-pod" policy file.

TASK 6: HEALTH PROBE CONFIGURATIONS (3 Standard Types)
---------------------------------------------------------------
Define THREE types of health probe configurations:

TYPE A -- "bridge" (standard, fixed values):
  - Annotation: smaitic.com/kyverno/health-config=bridge
  - Fixed liveness + readiness probe values for the Bridge application.
  - Port and path are FIXED (not user-supplied).
  - Bridge is the internal project name for the admin/control-plane app.

TYPE B -- "nginx-static" (standard, fixed values):
  - Annotation: smaitic.com/kyverno/health-config=nginx-static
  - Fixed liveness + readiness probe values for Nginx serving static builds.
  - Used for static HTML/JS/CSS frontends; no server-side rendering.

TYPE C -- "custom" (user-defined port and path):
  - Annotation: smaitic.com/kyverno/health-config=custom
  - Additional annotations for:
      smaitic.com/kyverno/health-port  e.g. 3000, 5173, 5174
      smaitic.com/kyverno/health-path  e.g. /healthz, /api/health
  - For SSR apps like Next.js that run on non-standard ports (not 8080).

[BEST PRACTICE]:
  Types A and B should use preconditions to match the annotation value exactly,
  so the wrong probe config is never applied to the wrong workload type.
