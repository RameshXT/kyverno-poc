The Hidden Costs of a Custom Webhook
While powerful, managing your own custom webhook on EKS for Smaitic Labs brings several hidden complexities:
Availability Risks: Webhooks sit in the critical path of pod creation. If your controller pod crashes or its TLS certificate expires, the API
server will either block all new deployments (Fail Closed) or allow pods to spawn without necessary secrets and sidecars (Fail Open).

Debugging Friction: Developers running helm template locally will not see the injected volumes or initContainers. The "magic" only
happens inside the cluster, which makes local troubleshooting harder.
Race Conditions: Your custom webhook must safely order its mutations alongside other cluster webhooks (like the AWS VPC CNI) to
avoid overwriting patches.
Instead of a custom operator, consider these two industry-standard alternatives.

Alternative 1: Kyverno (The Better Webhook)
If you want to stick with the annotation-driven architecture, Kyverno is the modern standard. It is a Kubernetes-native policy engine that acts as
the mutating webhook for you.
Instead of writing a custom controller in Go, you write a YAML ClusterPolicy. When Kyverno sees your annotation (e.g.,
[smaitic.com/inject-server-defaults](https://smaitic.com/inject-server-defaults): "true"), it patches the pod spec on the
fly.
No Code to Maintain: You only maintain YAML policies, not controller logic, leader election, or TLS certificates.
Idempotent Patching: Kyverno safely handles JSON/Strategic Merge patches without conflicting with other webhooks.
Dry-Run Mode: You can test policies without breaking the cluster.

If your goal is simply to DRY (Don't Repeat Yourself) your Helm codebase, a Helm Library Chart is often the safest path. You extract all the

preconditions to split the logic. Rule 4 initializes the array natively if the developer did not define one, while Rule 5 injects at index 0 if other
init containers (like database migration scripts) are already present.

Security Posture Overview
Because Kyverno operates as a Kubernetes Admission Controller (which intercepts and can mutate/block API requests before they are
persisted), its own security posture is heavily scrutinized. Overall, its security track record is excellent, backed by rigorous third-party auditing
and adherence to software supply chain standards.
Here is a breakdown of Kyverno's security posture:
1. Software Supply Chain Security (SLSA 3)

The Kyverno project places a heavy emphasis on securing its own artifacts.
SLSA Compliance: Kyverno achieves SLSA (Supply-chain Levels for Software Artifacts) Level 3 compliance. This means its build process
is highly resistant to tampering.
Image Signing & Provenance: All Kyverno container images, Helm charts, and manifests are signed keylessly using Cosign (part of the
Sigstore project). Users can mathematically verify that the Kyverno binaries running in their cluster were genuinely produced by the official
Kyverno GitHub Actions build pipeline.
2. Independent Security Audits
To maintain CNCF Graduated status, Kyverno undergoes continuous security reviews:
Third-Party Audits: Kyverno regularly passes independent security audits sponsored by the CNCF (most notably a comprehensive audit
in 2023).
Fuzzing: It is integrated into OSS-Fuzz. In 2023, an extensive fuzzing audit successfully identified and patched edge-case bugs, and fuzz
testing now runs continuously against the codebase.
TAG Security Assessment: The project has completed joint security threat modeling with the CNCF Technical Advisory Group for
Security (TAG Security).
3. Secure by Default Architecture
When you deploy Kyverno, the pods themselves conform to the strict Kubernetes Pod Security Standards (Restricted profile):
Containers run as non-root (and drop all privileges/capabilities).
The root filesystem is mounted as read-only.
Privilege escalation is explicitly denied.
4. Operational Security Considerations (The "Fail Mode" Factor)
The main security consideration for the user is how Kyverno handles API server timeouts. Because Kyverno is a webhook, you must configure
its failurePolicy:
Fail Closed (failurePolicy: Fail): If Kyverno crashes, Kubernetes blocks the creation of new pods. This is highly secure but can
cause cluster outages if Kyverno goes offline.
Fail Open (failurePolicy: Ignore): If Kyverno crashes, Kubernetes allows pods to spin up without Kyverno's checks. This ensures
high availability but means malicious or non-compliant pods could bypass your security policies.

The Verdict
Kyverno's security posture is robust, transparent, and aligned with modern zero-trust and supply chain security frameworks. You are adopting a
project that is built to guard production environments and treats its own code integrity with the same level of paranoia.

However, these defaults are rarely sufficient for production environments. As an admission webhook, Kyverno sits in the critical path of the
Kubernetes API server. If it lacks resources, API requests will time out, potentially blocking cluster deployments.
Production Sizing Guidelines
For a standard production cluster with moderate policy enforcement, you should increase these baselines significantly:
CPU: Request 500m to 1000m (1 full core). It is a Kubernetes best practice not to set CPU limits for admission controllers to prevent CPU
throttling during API spikes.

Memory: Request 512Mi and set a limit of 1Gi to 2Gi. Memory consumption is heavily tied to the caching of cluster state required for
context-aware policies.
Key Drivers of Resource Consumption
If you see CPU spikes or OOMKills, it is usually driven by one of the following factors:
Wildcard Matches: Policies that match on * (all resources) force the Kubernetes API server to send every single cluster event to Kyverno.
Even if the policy eventually skips the resource, the network and parsing overhead is massive. Always scope policies to specific resource
kinds or namespaces.
Generate Rules with Synchronization: Policies that clone and synchronize resources (like copying secrets across namespaces) require
Kyverno to actively monitor the source resource for changes.
Background Scanning: Kyverno periodically scans existing cluster resources against new policies. In large clusters, this background
controller requires dedicated scaling separate from the admission webhook.
API Calls: Policies that make external REST API calls or query the Kubernetes API server during evaluation will hold requests open
longer, requiring more memory to handle concurrent connections.

Kyverno that you must be aware of: the interaction between JSON Patches and Kyverno's Auto-Gen feature.
Here is exactly how Kyverno handles this scenario and how you need to tune it.

The Catch: JSON Patches Disable Auto-Gen
Normally, when you write a Kyverno policy targeting a Pod, Kyverno's auto-gen feature automatically translates that rule upstream. If you create
a Deployment or CronJob, Kyverno patches the template inside the controller once, and the controller handles spawning the actual pods.
However, Kyverno does not support auto-gen for patchesJson6902. Because JSON paths are rigid (e.g.,
/spec/containers/0/command/0), Kyverno cannot safely guess how to translate that path up into a CronJob's structure (which would be
/spec/jobTemplate/spec/template/spec/containers/0/command/0).
What this means for your cluster: Instead of mutating the CronJob once when you deploy it, Kyverno will intercept and mutate every single
Pod the CronJob spawns, precisely at the moment the CronJob creates it.
If you have 100 CronJobs running every 3 minutes, Kyverno will process 100 admission webhook requests every 3 minutes.

Can Kyverno handle the load?
Yes. A properly scaled Kyverno deployment can easily handle hundreds of admission requests per second. However, because CronJobs tend to
fire at the exact same second (e.g., exactly on the 3rd minute mark), they create sudden "thundering herd" spikes against the Kubernetes API
and the Kyverno webhook.
To ensure your cluster remains stable, you must implement these three safeguards:
1. Keep background: false (Crucial for CronJobs)
By default, Kyverno runs background scans to generate compliance reports. Short-lived CronJob pods cause massive database churn if
Kyverno tries to generate a report for a pod that only exists for 30 seconds. The policy provided earlier already includes background: false at
the top level to prevent this.
2. Scope the match block tightly
Kyverno's performance degrades if it has to evaluate complex rules for every pod. Because our policy uses:
match:
any:
- resources:
kinds:
- Pod
annotations:
smaitic.com/inject-secrets: "?*"
...the Kyverno webhook drops the request almost instantly if the pod lacks the annotation, saving significant CPU cycles. Never use wildcard
matching (*) without strict annotation or namespace filters in high-churn environments.
3. Over-provision Kyverno's CPU
Because CronJobs fire in simultaneous bursts, Kyverno needs burstable CPU to process the webhooks quickly. If Kyverno gets CPU-throttled,
pod creation will time out. Ensure Kyverno is running with High CPU Requests (e.g., 500m to 1000m) and NO CPU Limits.

Alternative: Target the CronJob Directly
If you find that Pod-level mutation is causing too much API server overhead, you can bypass the Pod webhook entirely by writing a policy that
targets the CronJob specifically.
You would change the match kind to CronJob and update the JSON Patch path to match the CronJob schema:
mutate:
patchesJson6902: |- op: add
path: "/spec/jobTemplate/spec/template/spec/containers/0/command/0"
value: "/scripts/app_launcher.sh"
This forces the mutation to happen only once when the CronJob is initially deployed to the cluster, completely eliminating webhook overhead
during the actual 3-minute scheduled runs.

User prompt: If I target cronjob directly, how will helm diff react to it? During helmfile release, I don't want these changes to flag, because they
will cause unnecessary noise during regular release.
Response: helm diff will flag every single mutated CronJob on every release, and it will be incredibly noisy.
Because Helm tracks the CronJob resource in its release secrets, comparing your local chart against the live cluster will immediately detect
Kyverno's modifications. Helm will assume someone manually tampered with the live cluster and will show a massive red diff, proposing to
delete the injected initContainers, volumes, and modified command array to revert the cluster back to your local state. (If you proceed with the
release, Helm will remove them, and Kyverno will just immediately re-inject them, resulting in a perpetual tug-of-war).
This exact CI/CD conflict is why industry-standard injectors (like Istio and Vault) never mutate parent controllers like Deployments or
CronJobs.

Why Pod-Level Mutation is the Standard
When you target the Pod instead of the CronJob:
Helm stays completely clean: The CronJob resource in the cluster remains pristine and identical to your local chart. helm diff sees no
changes.
The magic is downstream: The mutation only occurs invisibly at the exact moment the CronJob controller requests the API server to
create a Pod.

Handling the Webhook Load
While a */3 minute CronJob sounds frequent, it is negligible for a platform tool.
One CronJob running every 3 minutes is 20 Pods per hour.
Even if Smaitic Labs runs 100 of these CronJobs concurrently, that is only ~33 webhook requests per minute.
A properly resourced Kyverno deployment (2 replicas, 1Gi memory, burstable CPU) handles thousands of webhook requests per minute
easily.
The operational friction of a noisy helmfile diff in your CI/CD pipelines is a significantly worse engineering problem than the minimal API
server overhead generated by Pod-level mutations.

If you must avoid the Webhook overhead entirely
If you are strictly opposed to Pod-level webhook interception, Kyverno is the wrong tool for this specific job. Pure helm-diff (which Helmfile
relies on) does not have robust mechanisms for ignoring specific nested JSON fields like spec.jobTemplate...command[0]. (GitOps tools like
ArgoCD have an ignoreDifferences feature for this, but Helmfile does not).
To solve both problems—zero webhook overhead and perfectly clean Helm diffs—you must shift the logic entirely out of the cluster and into your
CI/CD pipeline using a Helm Library Chart.
